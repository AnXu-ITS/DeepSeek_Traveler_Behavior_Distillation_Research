# Phase B.5B — Demand Loading Sweep 最终结果与决策

## 结论：需求单边扩展无法在可行范围内产生拥堵

- VKT 从 1k 到 40k **完美线性**（×39.6），而延误纹丝不动（0.52→0.54 s/passage）——
  网络交互效应为零，所有车辆自由流。
- 定量解释：40k 人 → ~11,300 辆 car 的 142,538 km VKT 分摊到 **62,507 条使用中的链路**；
  换算峰值利用率 ≈ 27 veh/h/车道公里，仅为供给容量（600–2,000 veh/h/车道）的 **~2%**。
- 达到"轻度拥堵"（利用率 ~50–70%）需要 **~20–30× 当前加载，即 N ≈ 80 万–120 万 agents**
  ——超出任何可行的构建预算（40k 构建已 ~70 CPU 分钟），需求单边路径**到此为止**。

## 为什么真实供给如此"抗拥堵"（诚实归因）

1. OSM 转换把**每条道路的每个方向、每条支路**都建模为独立链路，容量按 highway 类别
   的饱和流率直接赋值——**没有路口延误**（信号周期损失、让行、行人干扰），而真实城市
   拥堵主要由路口瓶颈产生，而非路段容量本身。
2. 区域 3,520 km 路段（双向计），人口密度需求在 1-trip/agent 设定下天然偏低。

## 决策点（请选择，N* 未冻结，Phase C 不启动）

| 方案 | 内容 | 成本 | 评价 |
|---|---|---|---|
| **A（推荐）** | **供给侧标定而非"篡改"**：仅对城市道路施加路口容量折减（capacity × 0.35–0.45，相当于每周期有效绿信比），主干道不变；标定依据与系数写入论文 method（标准交通工程做法）。N*=10k 或 20k 即可出现轻中度拥堵与动态范围。 | 一次标定 + 复跑 1 个 sweep 点 | 网络拓扑保持真实；与"不篡改网络"不冲突——调整的是**容量标定精度**，不是伪造拥堵 |
| B | 需求加码：2 trips/agent + N=80k–100k（缓存化构建 ~1.5–2h/场景 × 6 场景） | 12+ 小时构建 | 能出拥堵，但 Phase C 节奏被构建拖死；且 1-trip 基线口径丢失 |
| C | 接受 free-flow：N*=40k，Phase C 网络级结论仅作方向性表述 | 0 | 牺牲 "Behavioral adaptation → Network consequence" 的量级证据，正是本次 B.5 要保住的 |

**建议 A**：这是交通仿真工程的标准做法（MATSim 官方同样建议对 OSM 转换网络做容量/信号
标定），可以在论文中如实声明"容量经路口有效绿信比标定"，证据链完整且诚实。
